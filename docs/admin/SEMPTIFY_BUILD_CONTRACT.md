## PART 1 — Module Documentation Schema

Every module/function must ship with this record completed **at build time**, as part of the definition of "done." No function is considered complete until this record exists alongside it.

**File location:** Each module ships its own `module_contract.json`, colocated in the module's folder — this is the source of truth, not a hand-maintained central file. A registry view (`docs/registry/module_contracts_index.json`) may exist for browsing, but it is generated by scanning per-module files, never authored by hand, to avoid the staleness pattern already flagged elsewhere in Semptify docs.

**Relationship to `FunctionGroupContract` [AMENDED]:** Semptify already has a code-level contract system — every reusable API surface registers a `FunctionGroupContract` via `register.py`, loaded by `app/core/contract_loader.py` (see `app/core/module_contracts.py` and Known Failure #16). The two systems have different jobs and must not be conflated:

- `FunctionGroupContract` **enforces** — it is machine-checked at runtime; if a field or method is not in it, it does not exist.
- `module_contract.json` **documents** — it is the human-readable record (process description, input provenance, preview/review states, narration slots).

Where the two overlap (`inputs`, `outputs`, dependencies), `module_contract.json` must be **generated or derived from the registered contract**, not hand-written as a divergent copy. Hand-authoring the same fields in both places is the documented staleness pattern this contract exists to prevent.

**Retroactivity:** Applies forward-only, to modules built after this contract is approved. Existing modules are flagged for a Part 1 record opportunistically during the standing documentation reconciliation pass — not a dedicated backfill project.

| Field | Description | Required |
|---|---|---|
| `module_name` | Human-readable name of the module/function | Yes |
| `layout` | Where it sits in the system; what calls it; what it calls | Yes |
| `inputs` | List of inputs: name, type, expected size/shape | Yes — derived from `FunctionGroupContract` where one is registered |
| `input_audit` | For each input: how it was obtained (upload, dropdown selection, auto-detect, typed entry, etc.) | Yes |
| `preview_state` | What the user sees before committing the action | If user-facing |
| `review_state` | What the user sees after the action, to confirm the result | If user-facing |
| `output_type` | File / record / UI state change / notification / other | Yes |
| `output_how` | Mechanism used to produce the output | Yes |
| `output_where` | Destination of the output (storage location, screen, downstream module) | Yes |
| `output_why` | Purpose the output serves | Yes |
| `process_description` | Plain description of what the module does | Yes |
| `process_context` | Trigger condition / precondition — when and why this runs | Yes |
| `narrative_events` | List of narrator event slots this module emits during execution (see Part 2) | **Optional until the Part 2 narrator runtime ships; required after [AMENDED]** |

## PART 2 — Real-Time Narrator (Slot Grammar)

The narrator reads each module's `narrative_events` and renders a live, plain-language sentence while the code runs. No custom narration code is written per function — the grammar reads the schema above.

> **Phasing [AMENDED]:** The narrator runtime does not exist yet. Until it ships,
> `narrative_events` in Part 1 is optional — modules may declare slots early, but
> no build fails for omitting them. The day the narrator runtime lands, the field
> flips to required for new modules. This prevents every module from carrying a
> dead field for an unbuilt system.

**Sentence structure:**

```
[Actor] [Verb] [Object] [Context clause]
```

| Slot | Source | Example |
|---|---|---|
| Actor | `module_name`, humanized | "The document uploader" |
| Verb | Current state, pulled from a fixed enum (`is checking`, `found`, `saved`, `is waiting for`, `flagged`) | "is checking" |
| Object | The input/output currently being acted on | "your lease PDF" |
| Context clause | `process_context`, phrased as "because..." | "because a new upload was detected" |

**Example rendered narrative:**
> "The document uploader is checking your lease PDF because a new upload was detected."
> "The timeline builder saved your contact record because you confirmed the entry."

**Verb enum (starting set — extend as needed):**
`is checking`, `is waiting for`, `found`, `did not find`, `saved`, `flagged`, `is comparing`, `confirmed`, `sent`, `is waiting on approval for`

**Rule:** Narrator output must follow the existing Semptify language rules — no adversarial framing, no "evidence"/"proof" language pre-court-date, no urgency language. Same voice rules apply here as apply to all tenant-facing copy.

## PART 3 — Resource Sourcing Contract (Information Composer intake)

This is a **separate contract** from Part 1 — it governs *content*, not code. Every item entering the Information Composer's resource files must pass through this record.

| Field | Description | Required |
|---|---|---|
| `source` | Direct citation/link to the original material | Yes |
| `source_type` | Research paper / news article / case study / statistical report | Yes |
| `fact_check_status` | Pending / Verified / Rejected | Yes |
| `fact_check_method` | How it was verified, and by whom | Yes |
| `fact_check_date` | Date last verified | Yes |
| `purpose_tag` | Which need it serves: strength / unity / confidence / reassurance / answers-unasked-question | Yes |
| `ai_generated` | Must be `false` — no AI-generated content permitted in this pool. This is a human attestation tied to `approved_by`; automated detection tooling may flag candidates for review but is not itself the gate | Yes (hard gate) |
| `approval_status` | Pending / Approved / Rejected | Yes |
| `approved_by` | Human approver of record | Yes, once approved |

**Approver of record [AMENDED]:** `approved_by` defaults to **Brad (Director)**. Another named human may be designated only by Brad's explicit written delegation recorded alongside this contract — agents must not improvise an approver.

**Hard rules:**
- No AI-generated material enters the resource pool — sourced human material only.
- Statistical reports require the original report, not a secondhand summary, wherever possible.
- Nothing is released to the Composer until `fact_check_status = Verified` and `approval_status = Approved`.
- Applies the same information-integrity rules already locked for Semptify: show sources, label opinion vs. fact, disclose AI-generated content elsewhere in the product, no vendor endorsement, ongoing (not one-time) re-checks.

**Suggested designation:** This intake process is its own subsystem — a **Resource Intake & Integrity Engine** — separate from general module builds. Its only job: ingest candidate material → tag it → fact-check it → route for human approval → release into the Information Composer's resource files. It does not do any Composer rendering work itself.

**Guardrail rule:** A lint/build check blocks any resource item from reaching the compiled output the Composer reads unless `ai_generated: false` and `approved_by` are both populated with a named human. This is the enforcement mechanism for the hard gate above — attestation is required, not optional, and unattested items fail the build rather than silently passing through. **Enforcement home [AMENDED]:** this check lives in `tools/guardrail_engine.py` (the existing repo guardrail runner), not a new parallel linter — a guardrail that isn't wired into the standing engine does not exist.

## PART 3B — Structured Fact Sourcing Contract (context_facts / Legal Citation Pipeline)

Part 3 governs curated *editorial* resources — research, articles, case studies — reviewed and approved one item at a time by a named human, aimed at reassurance/confidence/unity. That model doesn't fit structured factual data ingested at volume from official government sources (statutes, regulations, HUD notices, case citations). Per-item human sign-off on 119+ citations isn't a control, it's theater. The real control here is **deterministic resolution against known authoritative citation formats, a mandatory live source URL, and periodic audit sampling** in place of individual approval.

This is a separate, parallel contract to Part 3 — same rigor, different enforcement mechanism, because the content type is different.

### Schema — `context_fact` record

| Field | Description | Required |
|---|---|---|
| `fact_id` | Unique identifier for the fact/citation record | Yes |
| `citation` | The raw citation string as found (e.g. `42 U.S.C. § 1437f`, `HUD FHEO Notice 2020-01`) | Yes |
| `source_url` | Direct link to the official government/legal source (U.S. Code site, HUD.gov, state revisor's office, Westlaw record) | Yes |
| `source_authority` | Issuing body: U.S. Code, State Statute, HUD, Case Law/Westlaw, etc. | Yes |
| `jurisdiction` | Federal / state / municipal, plus state name if applicable | Yes |
| `resolution_status` | `Resolved` / `Unresolved` / `Disputed` | Yes |
| `resolution_method` | Which pattern/engine resolved it (e.g. `law_source_registry.py` pattern id/version) | Yes |
| `resolved_date` | Date the citation was successfully resolved | Yes, once Resolved |
| `taxonomy_subject` | Cross-reference into `taxonomy.py` / Law Library category | Yes |
| `last_verified_date` | Last date this fact's source was confirmed still live/accurate | Yes |
| `ai_generated` | Must be `false` — a `context_fact` is a resolved citation reference, never a model-generated summary or paraphrase of what a law says | Yes (hard gate) |
| `fabrication_check` | Pass/fail — passes only if the citation resolves to a real, reachable address at the official source | Yes (hard gate) |

### Hard rules

- No `context_fact` may be surfaced to a Page Composer or any consumer-facing endpoint unless `resolution_status = Resolved` **and** `source_url` is populated and reachable.
- `Unresolved` or `Disputed` citations are **quarantined** — held out of all consumer-facing endpoints until resolved or removed. They do not degrade gracefully into "partial" display; they simply don't ship.
- No per-item human sign-off is required — volume makes that impractical and it isn't where the risk lives. Instead:
  - A **periodic sampling audit** spot-checks a percentage of `Resolved` facts against their live `source_url`. **Cadence is mandatory, not advisory [AMENDED]:** the audit is carried as a standing entry in `MAINTENANCE_TASKLIST.md` (master repo) and executed as part of the scheduled documentation-reconciliation pass — "scheduled somewhere" means written into the standing task list, not just asserted here.
  - Any statute later amended, repealed, or superseded must be caught by this sampling and flagged for re-verification. Staleness is a real, ongoing risk here — law changes; a resolved citation today is not resolved forever.
- `ai_generated: false` is still a hard gate, same as Part 3, but means something more specific here: a `context_fact` is a resolved *reference* to an actual citation, never a model-authored summary, paraphrase, or interpretation of what a law means. **The moment anyone adds summarization or plain-language paraphrase of a statute's meaning, that content graduates into Part 3 / RIIE territory** and requires full editorial review — it is no longer a structured fact and this lighter contract no longer applies to it.
- **Guardrail:** a build/lint check blocks release of any `context_fact` lacking `resolution_status: Resolved` + a populated `source_url`, mirroring the Part 3 guardrail pattern exactly — unattested/unresolved items fail the build rather than silently passing through. **Enforcement home [AMENDED]:** `tools/guardrail_engine.py`, same as Part 3.

### Designation

This is governed by a distinct, named subsystem — the **Legal Citation Resolution & Verification Engine** — effectively the existing `law_source_registry.py` + `gatherer.py` + `taxonomy.py` pipeline, formalized as a standing subsystem with the same governance tier as the Resource Intake & Integrity Engine. RIIE and this engine are siblings: two separate content pipelines feeding Composers, each with its own contract, each documented — not one undocumented shortcut alongside one documented one.

Run this after Parts 1–3 are locked, and before starting the first UI/UX assembly pass on the site, app, or templates.

- [ ] Confirm no module's `narrative_events` depend on a resource that hasn't cleared Part 3 approval (code-driven narration should never block on human-gated content)
- [ ] Confirm no `context_fact` reaches a consumer endpoint without `resolution_status: Resolved` and a populated, reachable `source_url` (Part 3B guardrail)

- [ ] Confirm none of this reopens Layer 3 (currently frozen) — this contract applies to Layer 2 MVP work and its supporting documentation/resource pipeline only
